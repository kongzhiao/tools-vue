# 开发规范

## 总原则

- 先读 `AGENTS.md`、公共规范和对应功能文档，再修改代码。
- 业务结果以后端为准，前端不重复实现身份匹配、金额计算或状态机。
- 只做需求要求的最小改动，不顺手重构无关页面。
- 工作区存在用户改动时绕开处理，不回滚、不覆盖。

## 页面与服务分层

推荐链路：

```text
.umirc.ts 路由 -> src/pages 页面 -> src/services 业务服务 -> Umi request -> 后端 API
```

- 新增页面放在 `src/pages/<业务域>/`。
- 新增业务接口优先放在 `src/services/<业务域>.ts`，页面只负责参数组织和交互状态。
- 公共交互放入 `src/components/`，不要在多个页面复制任务轮询、复制文本或文件下载逻辑。
- 类型优先明确定义；新增代码避免继续使用 `any`，接口类型与后端字段保持一致。

## 路由与权限

- 路由在 `.umirc.ts` 注册，业务菜单需配置稳定的 `path`、`component` 和 `access`。
- 页面级权限通过 `hasModulePermission`，按钮通过精确操作权限控制。
- 权限名称必须与后端 `permissions.name` 完全一致，例如 `参保台账明细:导入`。
- 前端隐藏按钮不构成安全控制；写接口和镇街数据范围必须由后端校验。
- 新权限需同时更新后端权限数据、`src/access.ts`、路由或按钮和对应功能文档。

## 表格与筛选

- 列表查询必须明确分页、筛选、排序和重置行为。
- 用户列表使用 `page + limit`；两个台账主要使用 `page + page_size`，不得混传后假设后端会统一解释。
- 姓名、身份证号、批次号等长文本使用省略和 Tooltip；复制功能不得把敏感数据写入日志或本地存储。
- 列设置使用稳定 `key`；保存到 `localStorage` 时需带模块前缀，避免页面间冲突。
- 镇街账号不应看到管理员专属字段和操作；仍需以后端返回和鉴权作为最终边界。

## 表单与状态

- 表单必填、枚举和金额精度应与后端校验一致。
- 不将 Toast 成功当作最终业务完成；异步任务需提示任务中心核验。
- 删除、下放、收回、筛查、通知和报销标记等操作必须二次确认。
- 状态展示沿用后端中文枚举，不在前端自行转换出新的业务状态。
- 编辑密码时不回显密码；空密码表示保持不变。

## CSV 导入导出

- 台账上传控件只接受 `.csv`，每次只上传一个文件。
- 提交时明确传递 `year`、`period` 或 `settlement_period`，不得依赖页面上一次残留选择。
- 导入弹窗说明匹配键、更新范围和不会执行的动作。
- 模板字段应与后端可识别表头一致；改动表头兼容范围时同步功能文档。
- 下载使用任务 UUID 中转，不向浏览器暴露服务器存储路径。

## 请求与错误处理

- 统一通过 `src/app.ts` 的 Umi 请求配置附加 Bearer Token。
- 登录和初始化流程的原生 `fetch` 是当前存量实现；新业务接口不要另建请求封装。
- 兼容 `msg` 和 `message`；兼容业务成功码 `0` 与任务成功码 `200`，但单个接口必须按其实际约定判断。
- `401` 时清理登录状态并引导重新登录；不要在控制台打印 Token、请求敏感数据或完整身份证/银行卡信息。

## 样式与可用性

- 沿用 Ant Design 与现有后台密集型布局，优先清晰、稳定、可扫描。
- 筛选区、统计卡、操作栏和表格分区保持一致；避免装饰性大卡片。
- 操作按钮按权限和状态显示，禁用时给出可理解原因。
- 桌面端长表格允许横向滚动；移动端相关页面需检查可操作性。

## 验证

- 纯文档：检查目录、链接、Markdown 表格和 Mermaid。
- 前端代码：按变更范围运行格式化、环境校验、构建或相关检查。
- 修改项目结构或文档后运行 `codegraph sync`。
- 如实记录未执行、失败和环境限制，不得写成已通过。
